1. Question

For each decision model of the cohort (§3), at its leaderboard setting: does it take risks better on the pilot's 200-position test after 10 games against GNUbg weak (GNU Backgammon 1.08 Beginner), with a block of text about its own earlier games in its prompt, than with no block?

There are two arms, each judged on its own:

  • Arm N, helper-written notes → decision player. After each game a fixed helper model (the writer, §4) reads the decision model's graded game record and writes notes with the pilot's lesson prompt and limits. The page says: helper-written notes, not self-written learning.
  • Arm W, worst mistakes (no writer). After each game a fixed script puts the 5 costliest decisions of this series so far (GNUbg grades) into the prompt as solved examples (§5).

Each arm has its own games: same dice schedules, never the other arm's games, decisions or trajectories. Notes and examples reset at the start of every series. Games count nowhere (no league, no leaderboard).

Verdicts are reported per arm, under the same rule. Neither arm is picked as "the" result.

2. The rule (verbatim from the live plan §2; decided by Ümit, #3060 and #3065)

Improved = both of these hold:

  1. risks found with lessons (the mean of the 5 tests after game 10) minus risks found with no memory (the mean of the 3 empty runs) is more than max(range of the model's own 3 empty runs, 5 points);
  2. right safety with lessons minus right safety with no memory is ≥ −5 points (right safety drops by no more than 5 points).
  • Range = max − min of risks found over the model's 3 empty runs, in percentage points.
  • The 5-point floor = 5 of the 100 positions where the risk pays. The Gemma pilot showed about 3 points of drift from re-asking alone.
  • This is an operational threshold, not a statistical test and not statistical evidence. The page says so.
  • Error rate (PR) is shown before and after; it is not part of the rule.

For Part 3, "with lessons" means "with the arm's block" (notes in Arm N, worst mistakes in Arm W). "With no memory" means that arm's own empty runs (§6).

  • all 5 series (10 games each, 10 lesson files each);
  • all 5 T10 tests, each with 200 of 200 positions answered (valid or invalid; no failed request left);
  • all 3 empty runs, each 200 of 200.

Until then its row shows live numbers and "running, n of 5 series", with no verdict text. A model that cannot complete is shown "incomplete" with the reason, and never gets a verdict from partial data.

8. Failed and invalid answers

  • Invalid answers (same rule as the leaderboard; Ümit #3060): a reply that names no option (empty after thinking, cut at the output limit, a non-letter). In tests: not re-asked, left out of the shares (risks found, right safety, error rate), and the count is shown. In games: a random legal play, as in the leagues; counted.
  • Failed requests (no reply: transport or HTTP error, quota 429, timeout): retried as in the leagues; a test position still unanswered is asked again later with the same prompt and context (after quota waits if needed) until 200 of 200.
  • A series interrupted part-way is played again from game 1 with the same dice (the pilot rule); the failed attempt's files are archived (attempt-N/), its lessons are not used, and its spend counts.
  • A lesson call that fails is retried until it returns.

How the rules are applied (hard stops, logged):

  • Before every billed step: expected step cost = the table's S or E until the model's cost check, then its measured S1 or E1. If billed total so far + expected step cost would pass $110 → rule (b): stop and report. If it would pass the share, or the live balance − $5 does not cover it → pause (above).
  • Before every request (Zeki #3085): caps are enforced before a request starts, never discovered after crossing. Every OpenRouter request (game, lesson call, test) first reserves its worst case in a hard ledger (the runner's budget ledger): every byte of the request body counted as an input token plus the request's whole output allowance (its max_tokens) at the list price — far above a typical request, so it is the safety margin. It is sent only if billed so far in the step + the reservations of every request already in flight + its own reservation stay within the step ledger's cap = min(1.5 × the model's estimate − that model's billed so far, $110 − billed total so far, live balance at the step's start − $5, the share − billed total so far). Otherwise it is refused unsent and the step ends at that boundary: a refusal from one of the first two limits is a stop (rule a or b), from the balance or share limit a pause; either is logged and reported, and a paused step is replayed by the resume rules (§8).

All stop rules use this booked amount (conservative).
