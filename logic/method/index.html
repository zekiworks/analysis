Method

How the two benchmarks are built, run and scored

SetupsMeasuresSourcesScoringTranslationRuns

Decision and chat setups

The setups and the methodology are those of the team's decision-model benchmark (its 40 decision-model setups, run with the same runner). A setup is one model behind one endpoint with its settings (reasoning level, request size, hardware); its name on these pages is the run's setup label.

  • Decision models (group Decision) score each answer option and return the chosen one with a probability per option (stored as probs_json). Their confidence is the probability of the chosen option.
  • Chat models (group Chat) write a reply that ends with an answer letter; they return no option probabilities, so their confidence is “not measured”. Gemma 4 31B and Qwen3.8-27B, run on our own GPU, are chat setups.
  • The “I don't know” variant (runs with mode dont_know) asks the same questions with a sixth option F, “I don't know”. A setup's standard run gives its accuracy; its dont_know run gives its non-hallucination. Chat setups have no dont_know run yet.
  • The view bar's MODELS row picks Decision (the default), Chat or All; every chart, card, table and tie group is computed within the chosen group.

Measures

  • Accuracy: right / N, N the questions the standard run answered without a request error (all asked questions once a run is complete), with the 95% Wilson interval. Chance is 20% (five options). By topic: the same share within each topic.
  • Tie groups: every pair of setups in the group compared on the questions both answered with the exact McNemar test, p-values Holm-corrected over all pairs; two setups share a letter unless the corrected p < 0.05 (a compact letter display, tb-next's tied_groups).
  • Non-hallucination (dont_know runs): I don't know / (I don't know + wrong), the share of the answers that were not right that were an honest “I don't know”; beside it the attempt rate (right + wrong) / N and the accuracy when answering right / (right + wrong). A setup that always chose F would reach 100% with no right answers, so read it with the attempt rate. The Non-hallucination view keeps this apart from (a) the probabilistic confidence of the standard runs (answers kept at 99%, right / wrong, AUROC), so a setup that works with probabilities is not ranked down for rarely choosing F; beside its F rate it shows tb-next's derived rate: the same setup's five-option run answering only where its chosen option's probability reaches the cut-off that keeps about the same attempt rate, the rest held back. With All chosen, this view shows the decision setups and the chat setups in separate sections, never in one chart.
  • Confidence (option probabilities): answers kept at the 99% threshold, those whose chosen option had probability ≥ 99%, counted right and wrong; the result card names the setup that kept the most answers with no wrong one. AUROC: the probability that a right answer's confidence is higher than a wrong one's (ties count half; 0.5 is no signal), over all questions and by topic.
  • Cost: the run's recorded cost (runs.cost_usd) over the questions it answered, per 1,000 and per 1M questions, always with its basis: “API bill” (what the provider charged), “maker's list price” (the maker's published per-token or per-request price applied to the run's usage), “estimated cloud-equivalent” and so on. Chat runs carry an estimated cloud-equivalent cost, not a bill: the wall-clock minutes in which the run was storing answers (from its answer timestamps, not the sum of concurrent request times), with a minute shared equally among runs answering on the same GPU, priced at Runpod's on-demand rate for an RTX PRO 6000 (96 GB, Secure Cloud), $2.49 per GPU hour (runpod.io/pricing, 5 November 2026), the same card as ours. A run without a recorded cost reads “not measured”. The third result card is the cheapest setup within 1 point of the best accuracy; the Accuracy-across-Cost chart's dashed line is the Pareto front.
  • Latency: wall time per request from our machine, the median and the 90th percentile (nearest rank) in milliseconds, and throughput in questions per minute from the run's first to its last stored answer (it depends on how many requests were in flight). The Accuracy-across-Latency chart uses the median.
  • Together: Logic and Math pooled, 3,288 questions. Every measure is computed on the pooled answers (accuracy = right / all pooled questions; kept at 99%, AUROC and “I don't know” over the pooled answers; latency over all pooled requests, questions per minute over the two runs' time; cost per 1,000 questions = the two runs' costs over the pooled answers). Only setups with a complete English run on both benchmarks are pooled; the others are listed as not in Together yet. Its by-topic table shows each benchmark as a whole, then the topics of both.

Scoring

  • Chat models: the prompt asks for ANSWER: X on the last line; the scored letter is the last match in the reply. A reply without a letter is scored wrong.
  • Decision models: the chosen option is the scored letter; its probabilities are stored as returned.
  • A request that failed (timeout, server error) is not scored: it is left out of N; the run retries it when resumed. When a run stored several attempts, the first successful one is scored.

The English questions

Every question is asked in English. The English texts were translated from the question bank by a model, with automatic checks (option keys, digits, LaTeX, tables, labels, leftover untranslated words); a text that still failed after one retry, or a question that depends on the original language's words or letters, is flagged and not asked. The answer key is the question bank's answer key.
